# Game Glitch Investigator

## Project title and summary

**Game Glitch Investigator** is a Streamlit number-guessing game that repairs and demonstrates common bugs in a small interactive application. A player chooses a difficulty, guesses the secret number, receives higher/lower feedback, and can track a score across limited attempts. The project matters because it turns debugging topics such as state, input validation, and testing into a concrete, playable example.

## Original project (Modules 1-3)

The original project is the **AI 110 Modules 1-3 Game Glitch Investigator**, based on the Module 1 Game Glitch Investigator starter. Its original goal was to have students investigate an intentionally broken Streamlit number-guessing game, identify its logic and state bugs, and repair the game. The starter provided a difficulty selector, secret number, hints, attempts, score, and a developer debug panel, with logic intended to be refactored and tested.

## Architecture overview

The [system diagram](diagrams/system-architecture.mmd) shows the player sending a guess or game action to the Streamlit interface. The interface reads and updates the game's session state and calls pure helper functions in `logic_utils.py` to select a range, parse input, evaluate the guess, and update the score. The diagram also shows how pytest and the example runner check behavior, with a human reviewing the results and any AI suggestions; saved outputs provide reproducible evidence.

## Features and design decisions

- **Difficulty ranges:** Easy is 1-20, Normal is 1-100, and Hard is 1-50; each difficulty also has an attempt limit.
- **Session state:** Streamlit session state retains the secret and game progress across reruns. This avoids changing the secret during a game.
- **Pure game logic:** Parsing, comparisons, ranges, and scoring are separated into `logic_utils.py`, making them testable without launching the interface.
- **Input behavior:** Guesses must be whole numbers. Empty or invalid text gets a clear error instead of being counted as a numeric guess.
- **Developer debug panel:** The panel exposes the secret and game state to make local testing easier. It is for development and should not be treated as a player-facing feature.

The main trade-off is that the project prioritizes readable, deterministic game logic and course-level testability over a production deployment. In particular, the debug panel intentionally reveals the answer, and automated tests cover the pure helpers rather than browser interactions.

## Setup instructions

Requires Python 3.10 or later.

1. Open a terminal in the repository and move into the application directory:

   ```bash
   cd applied-ai-system-final
   ```

2. Install the project dependencies:

   ```bash
   python3 -m pip install -r requirements.txt
   ```

3. Start the Streamlit application:

   ```bash
   python3 -m streamlit run app.py
   ```

4. Open the local URL printed by Streamlit, usually `http://localhost:8501`.

To run the fixed-input, logic-only demo instead of the interface:

```bash
python3 demo.py
```

## Testing summary

Run the test suite from `applied-ai-system-final/`:

```bash
python3 -m pytest -q
```

The current suite passes **22 tests**, covering correct/high/low guesses, whole-number input parsing and invalid input, difficulty ranges, and score updates. The fixed-input demo also reproduces the three sample outcomes above. The saved results are in [assets/test-output.txt](assets/test-output.txt) and [assets/demo-output.txt](assets/demo-output.txt).

What worked: isolating game logic made it possible to test edge cases quickly and reliably. What is not covered: the suite does not automate browser rendering, Streamlit button interactions, or rerun/state behavior end to end. This reinforced the value of testing pure logic separately while recognizing that a passing unit suite does not replace UI testing.

## Reflection

This project reinforced that debugging is a process of forming a concrete expectation, reproducing a mismatch, changing the smallest relevant part, and checking the result with tests. It also showed how separating interface code from game rules makes problems easier to reason about. Responsible-AI collaboration, suggestion review, bias, and system limitations are documented in [model_card.md](model_card.md).
